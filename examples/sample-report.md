### CRITICAL (1)

#### RC-001 · CRITICAL · Overselling the last unit under concurrent checkout

- **Verdict:** CONFIRMED
- **Location:** `app/Http/Controllers/OrderController.php:16`
- **Found by:** race-conditions
- **Category / root cause:** race / non-atomic read-check-decrement on products.stock

**What breaks.** Two buyers both get an order for the last unit, and stock goes negative.

**Exact trigger**

Product 7 has stock = 1. Two clients POST /api/checkout {"product_id":7,"quantity":1} at the same time.

**Evidence (hunter)**

- app/Http/Controllers/OrderController.php:13 reads stock
- app/Http/Controllers/OrderController.php:16 writes stock - quantity with no lock or WHERE guard

**Skeptic's evidence**

app/Http/Controllers/OrderController.php:16 saves the decremented stock unconditionally. Two parallel processes against stock = 1: both returned 201, 2 orders created, stock = -1.

The stock check (line 13) and the write (line 16) are separate statements with no lock, transaction or guarded UPDATE, so two requests can both pass the check.

**Expected vs actual**

Expected: one 201 and one 422. Actual: two 201s and stock = -1.

**Failing test** (written by the skeptic: `.swarm-court/20261025-113529-checkout/tests/CheckoutRaceTest.php`)

```php
it('sells the last unit only once', function () {
    $product = Product::factory()->create(['stock' => 1]);
    $results = Process::pool(fn ($pool) => [
        $pool->command("php artisan test:checkout {$product->id}"),
        $pool->command("php artisan test:checkout {$product->id}"),
    ])->start()->wait();
    expect(Order::count())->toBe(1)->and($product->fresh()->stock)->toBe(0);
});
```

**Suggested fix**

Replace the read-then-save with an atomic guarded update: `Product::whereKey($id)->where('stock', '>=', $q)->decrement('stock', $q)` and return 422 when it affects 0 rows.

### HIGH (1)

#### AZ-001 · HIGH · Any user can read any other user's order (IDOR)

- **Verdict:** CONFIRMED
- **Location:** `app/Http/Controllers/OrderController.php:21`
- **Found by:** authz-security
- **Category / root cause:** authz / show() returns the bound Order with no ownership check

**What breaks.** A logged-in user can read other customers' orders by changing the id in the URL.

**Exact trigger**

User A owns order 10. User B logs in and sends GET /api/orders/10.

**Evidence (hunter)**

- app/Http/Controllers/OrderController.php:21 show(Order $order) returns $order with no policy or user_id check
- routes/api.php:4 only applies auth:sanctum

**Skeptic's evidence**

app/Http/Controllers/OrderController.php:21 returns $order directly. The test as user B got 200 with user A's order.

show() has no authorize() call, no OrderPolicy exists, and route model binding loads any order by id.

**Expected vs actual**

Expected: 403 or 404. Actual: 200 with user A's order.

**Failing test** (written by the skeptic: `.swarm-court/20261025-113529-checkout/tests/OrderIdorTest.php`)

```php
it('forbids reading another user\'s order', function () {
    $order = Order::factory()->for(User::factory())->create();
    $this->actingAs(User::factory()->create())
        ->getJson("/api/orders/{$order->id}")
        ->assertForbidden();
});
```

**Suggested fix**

Add an OrderPolicy::view that checks `$order->user_id === $user->id` and call `$this->authorize('view', $order)` in show().
